# NYC Taxi Lab — CRISP-DM Research Report

## 1. Business understanding

The product estimates taxi fare and travel time before a ride begins, while giving data scientists enough monitoring context to trust or challenge the estimate. Success means useful estimates, transparent uncertainty, low latency, and a repeatable experiment log.

## 2. Data understanding

The training schema follows the Kaggle NYC Taxi Fare Prediction fields: pickup/drop-off coordinates, passenger count, pickup timestamp, and fare target. This repository ships a deterministic synthetic generator so the project runs without private credentials or a large download. Production use should replace it with licensed trip records and document geographic and temporal coverage.

## 3. Data preparation

The pipeline derives great-circle distance, hour-of-day rush indicator, weekend indicator, and bounded passenger count. Invalid coordinates and impossible trips should be rejected upstream. The API recomputes distance from coordinates so clients cannot accidentally provide an inconsistent feature.

## 4. Modeling

The champion is a regularized linear Ridge model: interpretable, fast, and easy to export. It is compared with a mean-prediction baseline. The current artifact is intentionally small and human-readable; a production implementation should version the complete preprocessing graph and use a model registry.

## 5. Evaluation

Metrics are generated by `train.py` with a fixed seed and an 80/20 chronological-style split. Track RMSE, MAE, R², calibration/coverage of the uncertainty range, latency, and segment error by distance, borough, hour, and passenger count. These are simulated pipeline-validation metrics, not Kaggle leaderboard claims.

## 6. Deployment and monitoring

Flask exposes `/api/predict`, `/api/metrics`, and `/api/health`. Recommended production monitors are feature drift (PSI), missingness, prediction distribution, residuals, range coverage, p95 latency, and error rate. Retrain on meaningful drift, not on a fixed calendar alone.

## Autoresearch-style hill climbing

The experiment discipline is baseline-first: change one variable, run the same evaluation, keep only improvements, and log the reason. Candidate sequence: mean baseline → unregularized linear model → Ridge α=0.8 → Ridge plus derived distance/rush features. The final candidate is retained for interpretability and speed; future work should test gradient boosting, spatial clusters, and calibrated quantile models.

## Limitations and next steps

The demo does not call a routing engine, so the drawn line is a visual straight-line route and duration is model-derived. Add a licensed routing provider, borough-aware features, real trip records, CI tests, authentication, rate limiting, and a model registry before production deployment.
